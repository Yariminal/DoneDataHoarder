# Iteration 3 acceptance plan

This cycle addresses the quality gaps observed in [Iteration 2](ITERATION_2_VALIDATION_REPORT.md). Run all checks on disposable, isolated collections. Original ZIPs and private corpus evidence stay outside the repository. A `content_verified` analysis means the model saw readable content; it does not certify every interpretation or make a proposal safe.

| Area | Owner | Acceptance evidence |
| --- | --- | --- |
| Sequence duplicate review | Dependency and product | A labeled set includes adjacent frames, distinct template images, and genuine copies. Report keeper-relative candidate precision and recall with numerator/denominator, including the known false-match pattern. Numbered families appear as compact, sampled comparisons with the unsampled count explicit. Non-exact trash remains individual-only. |
| Naming quality | Product | Hand-review a synthetic and private holdout mix of documents, technical drawings, renders, scripts, and project/version IDs. Report identity retention, unsupported specificity, signed-number/ordinal handling, and useful-rename rate with denominators. Suggestions derive from each file's own verified evidence; uncertain labels remain reviewable as such. |
| Linked assets | Dependency | Parse verifiable AI, PSD, and HTML references. Preserve original paths where references cannot be inspected. Exercise a bundle-level plan and consuming-app check where practical; document unsupported shapes without claiming coverage. |
| Analysis scale | Scale | Benchmark optional representative-frame sampling and content-hash/model/extractor cache on a controlled set. Show fresh, cached, sampled, skipped, and error counts separately; sampled files receive no borrowed description and remain eligible for later full analysis. Compare time, peak Python RSS, and quality with a full run. Provide a bounded preflight estimate for 100–500 GB roots before inference. |
| Browser review | Product implementation; root visual verification | Verify setup → estimate → run → review → preview → commit/recovery on desktop and narrow screens. Check keyboard order, visible focus, status announcements, candidate/keeper evidence, protected and uncertain states, and per-action preview errors. Record actual browser findings and fixes. |
| Project-aware organization | Product | Classify each indexed file as in a preserved project boundary, independently proposed for type/date/subject organization, retained in an existing folder with suitability unverified, or needing review. Report each count and examples. A credible manifest or linked resource bundle establishes the nearest project boundary; an unrelated file in the same Downloads/Inbox parent remains eligible. Any proposed move stays pending until human review, and no unchanged project is counted as an organized standalone file. |
| Final combined corpus gate | Root | After implementation and focused tests, extract the six source ZIPs into a new disposable combined collection. Run preflight, complete scan/enrich/analyze with explicit coverage and cache/sampling accounting, dedup/relate/propose/organize, review and dry-run. Select only justified operations, commit and undo, and compare original relative paths, bytes/hashes, directory topology, database paths, foreign keys, and source ZIP hashes. Record wall time and sampled process RSS separately from Ollama/GPU usage. Then start the app for user inspection. |

No precision, recall, useful-name rate, or end-to-end safety claim is accepted without its measured denominator and review evidence.

The synthetic naming examples in `tests/test_quality_iteration3.py` are regression controls authored with this implementation, not an independent holdout. The quality gate also requires unseen hand-reviewed examples with labels and denominators before a naming rate is reported. Project preservation includes the selected root itself when it contains an explicit project manifest. The organization coverage endpoint distinguishes preserved, proposed, existing-folder-retained (structural heuristic only), and needs-review files; "fully organized" requires explaining every remaining needs-review file rather than equating zero operations with success.
